# Agent Note: 草稿文章日期的 GMT 缺失回退

Status: implemented

## Problem

2026-10-11实站[封面元数据验收](../architecture/2026-10-08-hls-loading-and-upgrade.md#featured-image-and-cover-metadata-validation-2026-10-11)发现，新保存的未发布草稿前台显示1970-01-01。WordPress允许草稿的`post_date_gmt`为零日期；此时`get_post_time('U', true)`返回`false`，`poi_time_since()`将其作为0参与计算和格式化。正文与列表还直接对GMT字段调用`strtotime`，同类缺失会得到错误日期。

## Decision

在[theme_plus.php](../../../../inc/theme_plus.php)提供统一文章时间读取：优先沿用`get_post_time('U', true)`及其过滤器，失败时以WordPress的`get_post_timestamp()`按站点时区解析本地文章日期，返回真实Unix时间戳。`poi_time_since()`拒绝非数字输入，合法的0及负时间戳仍可显示。三种头图、两种正文标题和五种列表日期统一调用此入口。

保留有效文章的GMT优先级、30天相对日期阈值、`time_zone_fix`和日期格式；不改有效评论日期、写回数据库、修改时区配置或为草稿编造当前时间。

读取的是WordPress交给主题的文章对象。WordPress7.1在具有编辑权限的非定时草稿预览查询中，会临时将`post_date`改为当前站点时间；主题遵循这个预览值，因此预览可显示“0秒前”。这不等同于主题把所有无效日期替换为当前时间，也不写回草稿的保存日期。

## Existing record audit

已检索活跃笔记中的`poi_time_since`、`post_date_gmt`、草稿和文章日期：没有持有该读取策略的已有决定。[HLS笔记](../architecture/2026-10-08-hls-loading-and-upgrade.md)仅部分重叠，保留缺陷发现与媒体验收；[分层验证](../testing/2026-10-07-compatibility-evidence.md)约束测试证据范围。新篇负责日期缺失、时区和返回值约定，不翻转原HLS决定。

## Alternatives considered

- 全部改用`get_post_timestamp()`：最简洁且能正确解释草稿本地日期，但站点时区改动后本地与GMT可能不一致，会改变已有文章的优先来源，也绕过原头图的`get_post_time`过滤器，因此不采用。
- 将`get_post_time`的GMT参数改为false：修改少，但其`U`格式会把时区偏移再加进时间戳，不能直接与Unix `time()`比较；因此不采用。
- 有效GMT优先、缺失才按站点时区回退（采用）：保持已发布文章既有来源，修复草稿及其他缺GMT文章；代价是维护一个小型共享入口和时区回归。
- 仅在格式化函数把false换成当前时间：能掩盖1970，但刷新时会重新变成“刚刚”，且没有恢复文章真实日期，因此不采用。

## Verification

2026-10-11在隔离的Windows/SQLite WordPress中复现旧路径：本地日期`2026-09-01 08:30:00`、Asia/Shanghai时区、GMT零日期时，旧读取为false并显示1970-01-01；本地日期对应的真实Unix时间戳为1788222600。

[WordPress烟雾检查](../../../../scripts/wordpress-smoke.php)增加九组日期样本，同时验证显式文章对象和默认全局文章：草稿、待审、命名时区、半小时偏移、夏令时、有效GMT优先、零日期、畸形日期、合法零值及负时间戳。另验证`get_post_time`过滤器返回0时不被本地日期覆盖，以及false/null不产生日期。内存`WP_Post`样本标记为raw，避免WordPress按虚构ID重新查询数据库；临时时区过滤器、时间过滤器和全局文章均在finally恢复。

WordPress7.0/7.1 × PHP8.0.30/8.1.34/8.2.33六组完整smoke通过，各组独立调试日志为空；九个变更PHP文件在三版PHP下共27项语法检查通过。WordPress7.1/PHP8.2另用真实临时草稿与附件渲染三种头图、两种正文和五种列表，十个入口均显示样本日期2000-09-01。该渲染检查只覆盖PHP输出，后续实站结果见下文。

首轮渲染夹具缺少完整查询上下文及附件文件记录，分别引发模板警告和头图不输出；补齐标准查询、模板加载方式及临时图片附件后通过，没有修改主题迁就夹具。旧调试日志曾导致后续smoke误判；保留旧日志后按运行隔离日志，最终六组均为空。

同日按现有打包排除规则制作本地安装快照，397个文件与工作副本逐字节一致，ZIP的CRC、单根路径、四份第三方许可及开发资料排除检查通过。包内保持Version3.7.0，没有伪造构建提交信息；未提交源码的资源回退继续遵循[构建来源策略](../architecture/2026-10-09-core-resource-build-reference.md)。隔离WordPress7.1/PHP8.2通过主题安装器实际安装该ZIP，安装后的397个文件与清单一致，完整smoke和十个模板渲染通过，运行时新增调试日志为空。安装器因隔离配置禁止外部HTTP而产生三条WordPress核心更新检查警告；该限制已与主题运行时结果分开记录，没有关闭外网隔离来消除警告。

### Deployed validation 2026-10-11

维护者手动安装本地测试快照后，内置Chromium实时确认草稿预览由1970-01-01变为“0秒前”；后台仍显示草稿，最后编辑时间为2026-10-11 10:59，特色图片保留。WordPress7.1核心的`WP_Query`预览分支解释了当前时间显示，主题没有再次修改日期实现。

页面主脚本版本为3.7.0，HTTP抽查`style.css`、`js/sakura-app.js`和`cdn/js/src/16.hls.js`的SHA-256均与交付包一致，旧`build-info.txt`返回预期404；这是公开资产抽查，没有宣称逐项读取了服务器全部397个文件。

现有特色图片及HLS元数据生成唯一封面视频，正文没有视频元素。实际播放至67.989秒，1920×1080；暂停前后时间固定47.451348秒，恢复后继续前进。跳转既有文章和历史前进时封面移除，两轮返回各获得新媒体源并实际播放至18.851秒和149.222秒，均为1920×1080。14次状态采样中播放器、看板娘、Canvas均各一个，媒体无错误，捕获的前台error/warn为空。最终视频暂停于149.370秒，草稿没有发布，未保存文章或全站设置。

此次补齐的是日期修复与原封面功能的实站复验；真实Safari、移动端、完整长视频、直播和故障恢复仍未覆盖。源码没有因部署验收再次修改，也没有新增提交、推送或正式Release。

## Consequences

文章时间读取集中到一个小型入口，缺少GMT的草稿可以使用其真实本地日期；无有效日期时输出空文本，合法0和负时间戳仍可显示。三种头图和七个正文/列表模板共享此策略，避免各自判断日期缺失；评论调用保持原样。

未知插件对`get_post_time`的非数字过滤结果将被视为不可格式化。未来日期显示为“之前”的既有行为及完整时区显示改造不在本轮范围，仍沿用原格式化方式。本地回归和测试站复验均已完成；服务器安装的是未提交工作副本的测试快照，不能因包内Version为3.7.0就将其当作既有正式版或新的CI构建。
